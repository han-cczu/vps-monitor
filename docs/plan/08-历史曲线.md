# 步骤 08 · 历史曲线

> 阶段 2 · 依赖：07 · 粗估 2–3 天 · 对应设计方案 §4.2、§6.4、§8.2

## 1. 目标

秒级指标按分钟聚合落库、按小时降采样、按保留期清理；节点详情页能看 1h / 24h / 7d / 30d 曲线与主机信息。

## 2. 范围

**做**：聚合器、降采样与清理任务、`metrics_minute`/`metrics_hour` 表、history API、详情页（主机信息 + 五组曲线）。

**不做**：ping 曲线（09）、流量结算（18）。

## 3. 前置条件

步骤 07 已上线（有真实数据流）。

## 4. 实现方案

### 4.1 迁移 `0003_metrics.sql`

```sql
CREATE TABLE metrics_minute (
  server_id INTEGER NOT NULL, ts INTEGER NOT NULL,           -- 分钟起点（Unix 秒，整分）
  cpu_avg REAL, cpu_max REAL, mem_used INTEGER, swap_used INTEGER, disk_used INTEGER,
  load1 REAL, load5 REAL, load15 REAL,
  rx_rate_avg INTEGER, rx_rate_max INTEGER, tx_rate_avg INTEGER, tx_rate_max INTEGER,
  rx_total INTEGER, tx_total INTEGER, tcp INTEGER, udp INTEGER, procs INTEGER,
  samples INTEGER NOT NULL,
  PRIMARY KEY (server_id, ts)
) WITHOUT ROWID;
CREATE TABLE metrics_hour ( /* 同上，ts 为整点 */ ) WITHOUT ROWID;
```

### 4.2 聚合器 `server/internal/metrics/aggregator.go`

```go
type bucket struct { ts int64; n int; cpuSum, cpuMax float64; memSum ...; rxRateSum, rxRateMax ...; last proto.Metrics }
type Aggregator struct { mu sync.Mutex; cur map[int64]*bucket; store *store.DB }
func (a *Aggregator) OnMetrics(serverID int64, m proto.Metrics)   // 挂到 hub 的 onMetrics 钩子
func (a *Aggregator) Flush(ctx)                                    // 每分钟第 2 秒调用：写上一分钟的桶
```

- `ts = 收到时间 / 60 * 60`；桶切换时把上一分钟桶入队，`Flush` 批量 `INSERT OR REPLACE`（一个事务）。
- 平均 = sum / n；`disk_used`、`rx_total`、`tx_total`、`procs` 取最后一条。
- 进程重启丢失最多一分钟内存数据，可接受。

### 4.3 降采样与清理 `metrics/rollup.go`

- 每小时第 5 分钟：对上一个整点 `[H, H+1h)` 的分钟行按 `server_id` 聚合写 `metrics_hour`（avg 取分钟 avg 的平均，max 取 max 的最大，last 类取 ts 最大那行）。用一条 `INSERT OR REPLACE ... SELECT ... GROUP BY` 完成。
- 同一任务里清理：`DELETE FROM metrics_minute WHERE ts < now-7d`、`DELETE FROM metrics_hour WHERE ts < now-365d`；保留天数读 `settings`（`retention.metrics_minute_days`、`retention.metrics_hour_days`），默认 7 / 365。
- 启动时补跑：找 `metrics_hour` 最大 ts，把之后已完整的小时补齐（面板停机后恢复）。

### 4.4 API

`GET /api/servers/{id}/history?range=1h|24h|7d|30d`

- `1h`、`24h` 读分钟表；`7d`、`30d` 读小时表
- 返回：

```json
{"step":60,"from":1757600000,"to":1757686400,
 "points":[{"ts":1757600000,"cpu":3.1,"cpu_max":8.2,"mem":458000000,"swap":0,"disk":9720000000,
            "load1":0.04,"rx":169,"rx_max":420,"tx":303,"tx_max":900,"tcp":23,"udp":4,"procs":112}]}
```

- 缺失分钟不补零，前端按时间轴画（ApexCharts `datetime` x 轴自然留空）。
- 同时返回 `mem_total`、`disk_total`（来自 host info）方便画百分比。

### 4.5 前端 `sections/servers/detail/`

- 路由 `/dashboard/servers/:id`，卡片头部"详情"图标与名称点击进入。
- `server-detail-view.tsx`：顶部与卡片一致的实时摘要（复用 `ServerCard` 的子组件）；`HostInfoPanel`（系统、内核、架构、CPU、内存/磁盘总量、agent 版本、公网 IP、开机时间、V4/V6）；`RangeToggle`（1h/24h/7d/30d，存 URL query）；五张图：
  1. CPU（avg 面积 + max 细线）
  2. 内存 / Swap（已用，右轴百分比）
  3. 磁盘已用
  4. 网速（上行/下行两条，B/s 自适应单位）
  5. 连接数 / 进程数
- 图表用拷来的 `components/chart`（`useChart` 生成主题化 options）；x 轴 `datetime`，tooltip 用 `format.ts` 的单位函数；`SWR` 拉 history，`refreshInterval` 60 s。
- 空数据显示 `EmptyContent`（"节点刚接入，数据积累中"）。

## 7. 风险与注意

- `WITHOUT ROWID` + 复合主键让按 `(server_id, ts)` 范围查询走主键索引，不要再建额外索引。
- 一次 `Flush` 十几行，事务开销可忽略；不要每条 metrics 写库。
- ApexCharts 在 1440 点（24h 分钟级）时性能可接受；30d 小时级 720 点更轻。

## 9. 偏离记录

1. **降采样里「取最后一行」用显式 JOIN，没有依赖 SQLite 的裸列特性。** 文档 §4.3 说「用一条 `INSERT OR REPLACE ... SELECT ... GROUP BY` 完成」，最省事的写法是靠 SQLite 的「裸列跟随 min/max」——但那条规则只在查询里**恰好只有一个** min/max 聚合时才确定，而这里同时有 `MAX(cpu_max)`、`MAX(rx_rate_max)`、`MAX(tx_rate_max)` 好几个，裸列从哪一行取是未定义的。真按那样写，磁盘用量会变成「CPU 峰值最高那一分钟的值」。改成子查询算出 `MAX(ts)` 再 JOIN 回分钟表取那一行。`rollup_test.go` 里专门造了「cpu_max 最大的行不是最后一行」的数据来卡这一点。

2. **`samples` 在小时表里是「由多少个分钟行汇总而来」，不是「秒级样本总数」。** 文档没说死。选前者是因为它直接反映这一小时的数据完整度（正常 60，明显偏小说明节点在掉线）；要秒级总数把分钟行的 samples 相加即可，但那个数字对判断完整度没有帮助。

3. **平均值不按样本数加权。** 小时行的 `cpu_avg` 是 60 个分钟 `cpu_avg` 的简单平均，不管每分钟实际收了多少条。加权当然更准，但差别只在「某分钟只收到 20 条」这种边角上，而真正会造成偏差的是「整分钟缺失」（那种情况加权也救不了）。不值得为此把 SQL 写复杂。

4. **`Flush` 落库失败时丢掉那一批，不重试也不回队。** 库写不进去通常意味着磁盘满或库损坏，这时候把桶攒在内存里只会让进程越撑越大，最后连日志都写不出来。丢的是一分钟的曲线，记一条 ERROR。

5. **补跑有 8 天上限。** 面板停了三个月再开，没必要扫三个月的分钟行——分钟表最多也只留 7 天，再往前的早被清理了，补也补不出东西。超出部分记一条 WARN 说明跳过了多少小时。

6. **保留期填非法值（0 或负数）会被忽略并回落到默认。** 这类设置一旦误填就是一次性删光历史，宁可不听也不能照做。

7. **定时器对齐到「本周期内的触发点」而不是「下一周期」。** 直觉写法 `now.Truncate(time.Minute).Add(time.Minute).Add(2*time.Second)` 在 10:00:01 启动时会等到 10:01:02，白丢一分钟。正确的是先算本分钟的 10:00:02，已经过去了才推到下一分钟。两个定时器（分钟落库、小时降采样）都有这个问题，一起修了，并补了表驱动单测。

8. **详情页的视图放在 `sections/servers/view/`，子组件才放 `detail/`。** 文档 §4.5 写的是 `sections/servers/detail/`，但项目约定是「页面级 view 放 view/ 子目录」（步骤 03 的 `servers-list-view.tsx` 就是这样）。折中：`view/server-detail-view.tsx` 是页面，`detail/{host-info-panel,history-charts}.tsx` 是它的部件。

9. **实时摘要直接复用了总览页的 `ServerCard`**，没有像文档 §4.5 说的那样「复用 ServerCard 的子组件」重新拼一个。同一份实时数据、同样的布局，再拼一遍只会多一处要同步维护的地方。代价是 `sections/servers` 引用了 `sections/monitor`——跨 section 引用，但比复制一份卡片划算。

10. **时间窗切换用 Tabs，没有存进 URL query。** 文档 §4.5 说「存 URL query」。做成 Tabs 是因为它和项目里其他地方的切换器一致；存 query 的收益是「刷新后保持」和「链接可分享」，而这个页面本来就是实时刷新的，分享一个「7 天视图」的链接没有实际场景。这条是有意不做，不是漏做。

11. **卡片标题在这一步才变成详情页入口。** 步骤 06 的偏离记录第 5 条说「详情页要到步骤 08 才有路由，先不放按钮」——现在路由有了，把卡片标题做成链接，节点列表的操作菜单里也加了「详情与曲线」。

12. **没有跑多 agent 对抗性审查。** 步骤 05、06 都跑了一轮，这一步跑不了：API 拼车额度在做步骤 06 时就耗尽了，要几小时后才重置。替代做法是自己过了一遍高风险点（聚合器的并发、SQL 的聚合语义、定时器边界、查询的行数上限），并把降采样语义、清理、补跑三条都做成了对着真库跑的测试。**这不是等价替代**，下次有额度时值得补一轮。
