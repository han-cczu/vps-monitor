# 步骤 19 · 告警通知

> 阶段 5 · 依赖：16、18 · 粗估 3–4 天 · 对应设计方案 §4.10、§8.5、§6.8

## 1. 目标

规则化的告警：离线、资源持续超阈值、节点流量与到期、ping 丢包、订阅用户用量、sing-box 应用失败/进程退出；Telegram 与 Webhook 通知；冷却与恢复；事件页可查。

## 2. 范围

**做**：`alert_rules`/`notify_channels`/`alert_events` 表、评估器、事件总线消费者、冷却与恢复、两种渠道、测试发送、前端三页。

**不做**：邮件、更多渠道（Bark/Server 酱可后加，接口留 `kind`）。

## 3. 前置条件

步骤 16（订阅事件）、18（流量与到期事件）；步骤 05 的事件总线、13 的核心事件。

## 4. 实现方案

### 4.1 迁移 `0010_alerts.sql`

```sql
CREATE TABLE alert_rules (
  kind TEXT PRIMARY KEY,                -- 见 4.2
  params TEXT NOT NULL DEFAULT '{}', enabled INTEGER NOT NULL DEFAULT 1, updated_at INTEGER
);
CREATE TABLE notify_channels (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, kind TEXT NOT NULL,   -- telegram | webhook
  config TEXT NOT NULL, enabled INTEGER NOT NULL DEFAULT 1, created_at INTEGER NOT NULL
);
CREATE TABLE alert_events (
  id INTEGER PRIMARY KEY, rule_kind TEXT NOT NULL, target_type TEXT NOT NULL, target_id INTEGER,
  level TEXT NOT NULL,                  -- info | warning | critical
  title TEXT NOT NULL, message TEXT NOT NULL,
  fired_at INTEGER NOT NULL, resolved_at INTEGER, notified_at INTEGER, dedupe_key TEXT NOT NULL
);
CREATE INDEX idx_alert_events_open ON alert_events(dedupe_key) WHERE resolved_at IS NULL;
CREATE INDEX idx_alert_events_fired ON alert_events(fired_at);
```

规则行在迁移里预置全部 kind 与默认 params。

### 4.2 规则与参数

| kind | 目标 | 默认 params | 判定来源 |
|---|---|---|---|
| `server.offline` | 节点 | `{minutes: 3}` | Registry `LastSeen` |
| `server.cpu` / `server.mem` / `server.disk` | 节点 | `{percent: 90, minutes: 10}` | 最近 N 分钟 `metrics_minute` 全部超阈值（内存里维护每节点最近 15 分钟环） |
| `server.traffic` | 节点 | `{percents: [80, 90, 100]}` | 步骤 18 事件 |
| `server.expire` | 节点 | `{days: [7, 3, 1]}` | 步骤 18 事件 |
| `ping.loss` | 节点 × 任务 | `{percent: 30}` | 步骤 09 的 30 次窗口丢包率 |
| `subscriber.quota` | 订阅用户 | `{percents: [80, 100]}` | 步骤 16 事件 |
| `subscriber.expired` | 订阅用户 | `{}` | 步骤 16 事件 |
| `core.apply_failed` | 节点 | `{}` | 步骤 13 事件 |
| `core.down` | 节点 | `{minutes: 1}` | `node_core.running=false` 且已安装、期望运行 |

### 4.3 评估器 `server/internal/alert`

- `evaluator.go`：每 60 s 跑一遍"轮询类"规则（offline、cpu/mem/disk、ping.loss、core.down）；"事件类"规则订阅事件总线立即处理。
- `dedupe_key = kind + ":" + target_type + ":" + target_id (+ ":" + 阈值)`；同 key 存在未 resolved 的事件 → 不重复发；条件消失 → 填 `resolved_at` 并发恢复通知（`server.offline`、`cpu/mem/disk`、`core.down`、`ping.loss` 有恢复；阈值类事件到点即 resolved，无恢复）。
- 冷却：同 `dedupe_key` 的下一次触发距上次 `fired_at` 小于 `settings.alert.cooldown_minutes`（默认 30）→ 记事件但不通知。
- 通知内容模板：`[级别] 标题\n节点：{name}\n{message}\n时间：{面板时区}`；Telegram 用 HTML 转义。

### 4.4 渠道 `alert/channel_*.go`

- Telegram：`config {bot_token, chat_id}`，`POST https://api.telegram.org/bot{token}/sendMessage`，`parse_mode=HTML`，10 s 超时，失败重试 2 次（30 s 间隔）
- Webhook：`config {url, secret?}`，`POST` JSON `{event: {...}, level, title, message, fired_at}`，有 secret 时加头 `X-Signature: sha256=HMAC(body)`
- 发送失败记日志与 `alert_events.notified_at` 保持 NULL，下一轮补发（最多 3 次）
- `POST /api/notify-channels/{id}/test` 发一条测试消息

### 4.5 API

| 方法 | 路径 |
|---|---|
| GET / PUT | `/api/alert-rules`（整表读写；PUT 数组） |
| GET / POST / PUT / DELETE | `/api/notify-channels` |
| POST | `/api/notify-channels/{id}/test` |
| GET | `/api/alert-events?page=&open=1&kind=&target=` |
| POST | `/api/alert-events/{id}/resolve`（手动关闭） |
| settings | `alert.cooldown_minutes` |

### 4.6 前端 `sections/alerts/`

- `rules-view.tsx`：一张表每规则一行：开关、名称、参数表单（数字/数组输入，内联编辑）、说明
- `channels-view.tsx`：渠道卡片列表；新增对话框按 kind 切换字段；"发送测试"
- `events-view.tsx`：`CustomDataGrid`：时间、级别 `Label`、规则、目标（可跳转节点/用户）、标题、状态（进行中/已恢复）、操作"关闭"；筛选：仅进行中、规则、目标
- 顶栏铃铛：进行中事件计数（SWR 30 s）；导航"告警"

## 6. 验收标准

- [ ] 停掉某节点 agent → 3 分钟后 Telegram 收到离线告警；重启 → 收到恢复；事件页两条记录状态正确
- [ ] 用 `stress` 把 CPU 压到 100% 十分钟 → 告警；停止后恢复
- [ ] 订阅用户超额 → 步骤 16 的事件触发 `subscriber.quota` 通知
- [ ] 把 ping 任务目标改为不可达 IP → 丢包告警；改回 → 恢复
- [ ] 手工 `kill` sing-box 并禁用 `Restart` → 1 分钟后 `core.down`；恢复后 resolved
- [ ] 冷却生效：反复启停 agent 30 分钟内只通知一次（事件仍记录）
- [ ] Webhook 用 `webhook.site` 或本地 `nc` 收到带签名的 JSON
- [ ] Telegram 不可达时事件 `notified_at` 为空，恢复网络后补发
- [ ] 单测：dedupe 与冷却逻辑、持续阈值判断（环形缓冲）

## 7. 风险与注意

- Telegram API 在国内不可达——面板在香港没问题；若面板迁回国内需走代理（`VM_HTTP_PROXY` 环境变量预留）。
- 评估器读 Registry 与内存环，不查库，避免每分钟大查询。
- 恢复通知只对"状态类"规则发，阈值类不发，避免噪音。
