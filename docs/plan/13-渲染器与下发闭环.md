# 步骤 13 · 渲染器与下发闭环

> 阶段 3 · 依赖：10、11、12 · 粗估 5 天 · 对应设计方案 §6.6 render/state、§9、§7.1–§7.4

## 1. 目标

面板上的入站/用户/证书变更 → 渲染出该节点的 sing-box 完整配置 → 预检 → 记修订 → 下发 → agent 应用 → 状态回流 → 面板可见；每用户流量增量入库。这是阶段 3 的核心闭环。

## 2. 范围

**做**：渲染器（四协议 + v2ray_api + 高级 JSON 合并）、本地预检、修订与对齐、变更合并（debounce）、`core.state/stats/logs` 处理、核心操作 API（安装/重启/重发/日志/修订/回滚）、快照 `core` 字段、统计入库。

**不做**：限额判断与自动停用（16）、前端页面（14）。

## 3. 前置条件

步骤 10（当前版本 + `current-local` 预检二进制）、11（agent corectl）、12（表与 CRUD）。

## 4. 实现方案

### 4.1 渲染器 `proxy/render`

```go
type Input struct { Server store.Server; Inbounds []model.Inbound; UsersByInbound map[int64][]store.Subscriber
                    Cert *store.Cert; Extra json.RawMessage; Version string }
type Output struct { Config []byte; SHA256 string; Ports []string; UserNames []string; InboundTags []string }
func Render(in Input) (Output, error)
```

- 用 Go 结构体（`map[string]any` 有序化：`encoding/json` 对 struct 按字段顺序输出，便于 diff）建 §9.3 的骨架；四个协议各一个 `buildXxx(inbound, users, cert)`。
- 用户条目：`name = "sub-{id}"`；vless `{name, uuid, flow:"xtls-rprx-vision"}`；shadowsocks `{name, password: ss_user_key}`；hysteria2 `{name, password}`；tuic `{name, uuid, password}`。
- 只放入 `enabled && auto_disabled == none` 的用户（`auto_disabled` 由步骤 16 维护，本步始终为 none）。
- `experimental.v2ray_api.stats.inbounds/users` = 本次全部 tag 与用户名。
- 证书：`cert_pem/key_pem` 按行拆成字符串数组内联到 `tls.certificate/key`。
- 高级 JSON 合并 `merge.go`：`extra.outbounds` 追加到 `outbounds`（tag 重复报错）；`extra.route.rules` 插到默认 `sniff` 规则之后；`extra.route.final` 覆盖默认 `direct`；其它顶层键（如 `dns`）允许直接覆盖并记 warn。
- `Ports`：vless `{port}/tcp`；shadowsocks `{port}/tcp` 与 `{port}/udp`；hysteria2、tuic `{port}/udp`。
- 输出 `json.MarshalIndent`（2 空格）便于修订对比与人工阅读。
- **单测**：黄金文件（`testdata/*.golden.json`）对比四协议各一、全协议一、无用户、带高级 JSON、无证书时 hy2 报错。

### 4.2 预检 `proxy/render/check.go`

`Check(config []byte) error`：写临时文件，`exec {DataDir}/corefiles/current-local check -c tmp`，10 s 超时；二进制不存在 → 返回 `ErrNoLocalCore`（上层记 warn 后放行，避免面板架构与托管架构不一致时卡死）。

### 4.3 对齐器 `proxy/reconcile.go`

```go
type Reconciler struct { db; hub; render; debounce map[int64]*time.Timer; inflight map[int64]*inflight }
func (r *Reconciler) NodeChanged(serverID, reason)          // 实现 Notifier：重置 5 s 定时器
func (r *Reconciler) Reconcile(ctx, serverID) error          // 定时器到期调用；也可由 API 强制调用
func (r *Reconciler) OnAgentHello(serverID, appliedRevision)
func (r *Reconciler) OnCoreState(serverID, st proto.CoreState)
```

`Reconcile`：

1. 读节点、入站、分配用户、证书、高级 JSON、当前版本 → `Render`
2. `sha` 与 `config_revisions` 最新一条相同 → 不新增修订；否则 `Check`，通过后 `revision = last+1` 插入，`node_core.desired_revision = revision`，`desired_version = current`
3. 若 agent 在线且无 inflight：发送 `core.apply{revision, version, sha, ports, config}`，记 inflight（60 s 超时）
4. agent 不在线：什么也不做，等 `hello` 时对齐

`OnAgentHello`：`applied_revision < desired_revision` 或 `installed_version != desired_version`（后者只提示不强制升级）→ 发送 `core.apply`。

`OnCoreState`：更新 `node_core`（installed/running/applied/sha/listening/firewall/last_error）；清 inflight；`error != nil` 时记事件 `CoreApplyFailed`（步骤 19 告警订阅）并按 10 s / 30 s / 60 s 重试 3 次（重试前不重新渲染）；广播快照。

inflight 超时（60 s 无 `core.state`）→ 记错误"agent 无响应"，允许下一次。

### 4.4 Hub 处理器

- `core.state` → `Reconciler.OnCoreState`
- `core.stats` → `stats.Ingest(serverID, msg)`：内存累加 `acc[(subscriberID, serverID)] += up/down`（名字 `sub-{id}` 解析失败的忽略）；每 60 s 一个事务：`UPSERT subscriber_traffic(period_start = subscriber 当前 period_start)`、`UPSERT subscriber_traffic_daily(today)`、`subscribers.traffic_used = SUM(当前账期 up+down)`（本步先按 up+down 计，模式留给 16 决定是否可配）；入站级计数只留在内存供核心页显示
- `core.logs` → 按 `ReqID` 投递到等待的 API 请求（`map[reqID]chan`，10 s 超时）

### 4.5 API

| 方法 | 路径 | 行为 |
|---|---|---|
| GET | `/api/servers/{id}/core` | `node_core` + 在线 + 当前托管版本 + 内存入站计数 + `pending`（desired > applied） |
| POST | `/api/servers/{id}/core/install` | 发 `core.action install`（当前版本、文件名、sha）；agent 离线 409 |
| POST | `/api/servers/{id}/core/restart` | `core.action restart` |
| POST | `/api/servers/{id}/core/apply` | 强制 `Reconcile` 并重发（即使 sha 未变） |
| GET | `/api/servers/{id}/core/logs?lines=200` | 同步等待 agent 回传，10 s 超时 504 |
| GET | `/api/servers/{id}/core/revisions` | 最近 20 条 `{revision, sha256, created_at, created_by, applied}` |
| GET | `/api/servers/{id}/core/revisions/{rev}` | 完整 `config_json` |
| POST | `/api/servers/{id}/core/rollback/{rev}` | 把该修订内容作为新修订插入（`created_by = rollback:{rev}`）并下发；注意回滚是"按当时的配置再发一次"，之后任何变更会重新渲染覆盖 |

### 4.6 快照

`servers[].core = {installed: bool, running: bool, version: string, users: int, pending: bool, error: string|null}`。

### 4.7 修订清理

每节点保留最近 20 条修订（rollup 任务里 `DELETE ... WHERE revision < max-20`）。

## 5. 接口与数据

见 4.5、4.6；`node_core`、`config_revisions`、`subscriber_traffic*` 开始有数据。

## 6. 验收标准

- [ ] 渲染黄金文件测试通过；`sing-box check` 对全部黄金文件通过（用真实二进制跑一次 CI job）
- [ ] 测试节点：点"安装" → agent 下载安装、`core.state` 回流，核心接口显示版本与 running
- [ ] 创建四个入站 + 一个订阅用户分配全部 → 5 s 内出现修订 1 并下发 → agent 应用 → `listening` 含五个端口 → `pending=false`
- [ ] 连续快速改三次备注/启停 → 只产生一次渲染与一次下发（debounce）
- [ ] agent 离线时改配置 → 修订产生但不下发；agent 上线 `hello` 后自动补发
- [ ] 故意让端口冲突（高级 JSON 里再加一个同端口入站）→ 预检或 agent 回滚 → `last_error` 显示原因，节点仍运行旧配置
- [ ] 用本地 sing-box 客户端连 VLESS 或 SS 入站跑 50 MB → 60 s 内 `subscriber_traffic` 与 `traffic_used` 增长量级正确
- [ ] `logs` 接口 10 s 内返回 sing-box 日志；agent 离线时 409
- [ ] 回滚到修订 1 后 agent 应用的 sha 与修订 1 一致

## 7. 风险与注意

- 渲染器是整个代理功能的"编译器"，字段名一字之差就是全节点故障——黄金文件必须覆盖每个协议，且用真实 `sing-box check` 验过。
- `desired_version` 与 `installed_version` 不一致时不要自动升级（升级会断连），只在页面提示。
- `traffic_used` 的统计方向（up+down）与节点流量的 `max` 模式不是一回事，这是给"人"限额，按双向总量最符合直觉；若要可配，步骤 16 加设置。
