# 步骤 07 · 部署上线

> 阶段 1 · 依赖：06 · 粗估 1–2 天 · 对应设计方案 §12 · 完成即里程碑 **M1**

## 1. 目标

面板以 Docker 形式跑在香港节点上，HTTPS 可用；agent 二进制与安装脚本由镜像自带；有发布流水线、备份脚本与 runbook。

## 2. 范围

**做**：多阶段 Dockerfile、docker-compose、Caddyfile、发布 CI（镜像 + agent 二进制）、首启流程、备份脚本、runbook 初版。

**不做**：sing-box 相关（10）、agent 自动更新（20）。

## 3. 前置条件

步骤 06；一台有域名解析的 VPS（香港），80/443 可达。

## 4. 实现方案

### 4.1 Dockerfile（仓库根 `deploy/Dockerfile`）

```dockerfile
# 1. 前端
FROM node:24-alpine AS web
WORKDIR /src/web
COPY web/package*.json ./
RUN npm ci
COPY web/ .
RUN npm run build

# 2. Go（server + agent 两架构）
FROM golang:1.26-alpine AS go
WORKDIR /src
COPY go.work go.work.sum ./
COPY proto/ proto/
COPY agent/ agent/
COPY server/ server/
COPY --from=web /src/web/dist server/web/dist
ARG VERSION=dev
RUN CGO_ENABLED=0 go build -trimpath -ldflags "-s -w -X main.version=$VERSION" -o /out/server ./server/cmd/server \
 && CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags "-s -w -X main.version=$VERSION" -o /out/agent/vps-agent-linux-amd64 ./agent/cmd/agent \
 && CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags "-s -w -X main.version=$VERSION" -o /out/agent/vps-agent-linux-arm64 ./agent/cmd/agent \
 && cp agent/install.sh agent/uninstall.sh /out/agent/

# 3. 运行
FROM gcr.io/distroless/static-debian12
COPY --from=go /out/server /app/server
COPY --from=go /out/agent /app/agent-dist
ENV VM_LISTEN=:9000 VM_DATA_DIR=/data
VOLUME /data
EXPOSE 9000
ENTRYPOINT ["/app/server"]
```

服务端启动时若 `{DataDir}/agent/` 为空或版本文件旧于 `/app/agent-dist/VERSION`，把 `/app/agent-dist/*` 复制过去（步骤 03 的静态托管读 `{DataDir}/agent/`）。这样升级镜像即升级可下载的 agent。

### 4.2 Compose 与 Caddy（`deploy/`）

`docker-compose.yml` 与 `Caddyfile` 按设计方案 §12.1；补充：

- `.env.example`：`PANEL_DOMAIN`、`VM_JWT_SECRET`、`VM_TZ`
- Caddyfile 可选片段（IP 白名单）：

```
panel.example.com {
    @allowed remote_ip 1.2.3.4/32 5.6.7.0/24
    handle @allowed { reverse_proxy server:9000 }
    handle { respond 403 }
    log {
        output file /data/access.log
        format json
    }
}
```

- 日志脱敏：`/sub/*` 的 query 不进日志——Caddy 用 `log { format filter { request>uri query { delete token } } }`，步骤 15 上线订阅时补齐。

### 4.3 发布 CI `.github/workflows/release.yml`

- 触发：推 tag `v*`
- 构建镜像（`docker/build-push-action`，`--build-arg VERSION=$TAG`，平台 `linux/amd64`；面板主机若是 arm 再加），推 GHCR
- 同时把 `agent` 两架构二进制与脚本作为 GitHub Release 资产上传（方便不走面板直接下载）

### 4.4 首启与运维脚本

- `deploy/backup.sh`：`docker compose exec -T server /app/server backup /data/backup/vm-$(date +%F).db`（服务端实现 `backup` 子命令，用 `VACUUM INTO`），保留 14 天；`crontab` 示例每日 03:00
- `deploy/restore.md`：停 server → 替换 `data/vm.db` → 起
- `docs/runbook.md` 初版：安装、升级（`docker compose pull && up -d`）、回滚（指定旧 tag）、看日志、初始密码找回（`docker compose logs server | grep initial`）、重置管理员密码（`/app/server reset-password admin` 子命令）

### 4.5 服务端子命令

`server`（默认运行）、`server backup {path}`、`server reset-password {username}`（打印新随机密码）、`server version`。

## 7. 风险与注意

- distroless 无 shell，排障用 `docker compose logs`；确实需要进容器时临时换 `alpine` 基础镜像。
- Caddy 数据卷（证书）要持久化，否则重启后重新签发可能触发 Let's Encrypt 限流。
- 面板若放在国内机房，域名需备案；本方案放香港。

## 9. 偏离记录

1. **`VM_AGENT_DIST` 做成了环境变量，不是硬编码路径。** 文档 §4.1 说「服务端启动时若 `{DataDir}/agent/` 为空或版本文件旧于 `/app/agent-dist/VERSION`，把产物复制过去」。实现成 `VM_AGENT_DIST`（镜像里设成 `/app/agent-dist`，本地开发不设就整个跳过），免得非容器运行时也去摸一个不存在的绝对路径。判断条件也简化了：比的是数据卷里的 `VERSION` 文件和当前二进制的版本号，不一致就覆盖——镜像里不需要额外放一个 VERSION 文件。
   同步只拷白名单里的四个文件（两个架构的二进制 + 两个脚本），和 `api/static.go` 的下载白名单一致；先写临时文件再改名，避免节点正好在这一刻下到半截。

2. **`server backup` 的路径参数是可选的。** 文档 §4.4 写的是 `server backup {path}`，实现成不给路径就默认写到 `{VM_DATA_DIR}/backup/vm-YYYY-MM-DD.db`，`backup.sh` 里就不用再拼一次日期。

3. **备份用 `VACUUM INTO` 而不是 `.backup`。** 设计方案 §12.3 写的是 `sqlite3 data/vm.db ".backup ..."`，那需要宿主上装 sqlite3 CLI，而 distroless 镜像里连 shell 都没有。改成服务端自己的子命令，调 SQLite 的 `VACUUM INTO`：同样是在线一致备份，还顺带整理了碎片，且不依赖任何外部工具。

4. **镜像以 root 运行。** distroless 提供 `nonroot` 变体，但数据目录是 bind mount（`./data:/data`），换成 nonroot 就得先在宿主上 `chown 65532`，装机流程里多一步、漏了的表现是「起来就崩」。容器里没有 shell、只有一个静态二进制，暴露面本来就小。要收紧的话把 bind mount 换成 named volume 再加 `user:`，这一点写在 Dockerfile 的注释里了。

5. **compose 里 `VM_TRUSTED_PROXIES` 固定为 `1`。** 前面就一层 Caddy。这一项必须和实际拓扑对上——填错会让登录限速和审计里的 IP 全变成 Caddy 的容器地址，或者反过来变成可以被请求头伪造。本机实测确认生效：Caddy 容器是 `172.20.0.3`，而服务端记录下来的 `public_ip` 是 `172.20.0.1`（真实对端），说明取的是 XFF 而不是 TCP 连接地址。

6. **「容器内存小于 100 MB」要分稳态和峰值说。** 实测分级归因：
   | 时刻 | RSS |
   |---|---|
   | 刚启动（已同步 agent 产物） | 13 MB |
   | 下发过前端之后 | 16 MB |
   | 登录一次之后 | 81 MB |
   | 连续登录四次之后 | 146 MB |
   涨的全是 argon2id 的工作缓冲：每次校验 64 MiB，并发闸放行 4 个（`api/router.go` 的 `maxConcurrentVerify`），所以理论峰值约 256 MiB。Go 的后台清道夫会把它还给系统——实测 146 → 77 → **16 MB**，约 4 分钟走完。
   **结论**：稳态 16 MB 远低于 100 MB，登录后会有几分钟的高位。这是 argon2 的固有成本（步骤 02 选的参数），不是泄漏。512 MB 的小鸡够用，但如果要跑在 256 MB 的机器上，得把 `maxConcurrentVerify` 或 argon2 的内存参数调下来——那是改安全参数，不在本步范围内。

7. **Caddyfile 用 `{$PANEL_DOMAIN}` 占位而不是写死域名**，域名从 compose 的环境变量传进去，同一份配置换台机器不用改文件。访问日志按天轮转保留 14 天，`format json`；query 不记（步骤 15 的订阅链接把 token 放在 query 里）。

8. **`.gitignore` 补了 `/deploy/data/` 与 `/deploy/.env`。** compose 起来之后 `deploy/data/` 里会有库、`jwt.secret` 和备份，原来的 `.gitignore` 只忽略了仓库根的 `/data/`，这些会被 `git add -A` 带进版本库。

9. **发布 CI 只构建 `linux/amd64`。** 文档 §4.3 说「面板主机若是 arm 再加」——多架构构建要起 QEMU，时间大概翻三倍，用不到就不开。agent 那边照常两个架构，它跑在节点上，arm 小鸡很常见。Release 资产附 `SHA256SUMS`。

10. **健康检查用 `/app/server version`。** distroless 里没有 shell 也没有 curl，`CMD-SHELL` 那套用不了；服务端自己的子命令是现成的、够轻，能证明二进制可执行。它探的是「进程活着」而不是「HTTP 可用」——真正的端到端可用性由 Caddy 的反代错误暴露。

### 待真机

三条都卡在「需要一台有公网域名的 VPS」上，本机造不出来：

1. **干净 VPS 上 15 分钟内可登录**——本机跑通的是同一份 `docker-compose.yml`（只用 override 换了端口和 Caddyfile），装 Docker 与填 `.env` 这两步没法在 Windows 上等价验证。
2. **Caddy 自动签证书、HTTP 自动跳 HTTPS**——ACME 要求域名能从公网解析到这台机器。本机用的是纯 HTTP 的 `:80` 站点，验的是反代与 WS 透传，不含 TLS。
3. **四台节点装 agent 全部在线**——本机只有一台 agent 且不是通过 `install.sh` 装的（跑的是编译好的二进制 + 手写 config）。`install.sh` 本身的真机验证从步骤 04 就欠着，见 `04-Agent-MVP.md` §6。

真机部署时按 `docs/runbook.md` §3「首次安装」走，把这三条补掉，M1 就算真正到手。

### 一个 Windows 上的小坑

Git Bash 会把 `docker compose exec -T server /app/server version` 里的 `/app/server` 改写成
`D:/Program Files/Git/app/server`。前面加 `MSYS_NO_PATHCONV=1` 即可。这只影响在 Windows 上
调试容器，Linux 上没有这个问题，所以没写进 runbook 正文。
