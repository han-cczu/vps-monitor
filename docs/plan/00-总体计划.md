# 实施计划总览

> 依据：《设计方案 v1.0》（`docs/设计方案.md`）。本目录把方案拆成 **20 个步骤、5 个阶段**，每个步骤一份实现方案文档，独立可开工、可验收。

---

## 1. 拆解原则

1. **每步一个可运行、可验收的增量**——步骤结束时系统处于可用状态，不留半成品。
2. **先打通端到端，再加深度**——阶段 1（步骤 01–07）就把面板上线、卡片跑起来；后面每个阶段只往上叠。
3. **接口先行，前后端可并行**——每个步骤文档给出该步新增的接口与数据结构，前后端可以分头做。
4. **高风险先验证**——sing-box 自编译与每用户统计（步骤 10）排在渲染器（13）之前，先把地基踩实。
5. **文档随代码走**——每步结束更新 `docs/protocol.md`（消息与接口）和 `docs/runbook.md`（运维），设计方案本身不改，改了就记到该步骤文档末尾的"偏离记录"。

## 5. 工程约定

| 项 | 约定 |
|---|---|
| 仓库 | 单仓 `vps-monitor/`，结构见设计方案附录 A |
| Go | 1.26；根 `go.work` 纳入 `agent`、`server`、`proto` 三个模块；模块路径 `vpsmon/agent`、`vpsmon/server`、`vpsmon/proto`（本地路径即可，开源时再换成 GitHub 路径） |
| Node | 24；包管理用 npm（starter 声明 yarn，README 同样支持 npm） |
| 端口 | 前端 dev 8080 → 代理到 Go 9000；生产只暴露 Caddy 80/443 |
| 环境变量 | 前缀 `VM_`：`VM_LISTEN`、`VM_DATA_DIR`、`VM_PUBLIC_URL`、`VM_JWT_SECRET`、`VM_TZ`、`VM_LOG_LEVEL` |
| 数据目录 | `{VM_DATA_DIR}/vm.db`、`/corefiles/`、`/agent/`、`/backup/` |
| 分支 | 每步一个分支 `step/NN-name`，合并到 `main`；每个里程碑打 tag `m1`…`m5` |
| 提交 | 小步提交，信息用中文或英文均可，写清"做了什么" |
| 迁移 | `server/internal/store/migrations/NNNN_name.sql`，goose 格式，只增不改；**步骤文档里的编号只是示意**，实际按开工顺序取当前最大编号 +1（步骤可能穿插进行，goose 不接受乱序） |
| 日志 | Go 用 `log/slog` JSON 输出；agent 与 server 一致 |
| 测试 | 纯逻辑（结算、渲染、密钥、限额评估）必须有表驱动单测；集成靠验收清单手工过 |
| 完成定义 (DoD) | 该步文档的验收清单全部勾掉；`go vet`/`tsc`/`eslint` 通过；`protocol.md`、`runbook.md` 更新；偏离设计之处记入文档末尾 |

## 6. 步骤文档的结构

每份步骤文档统一为：

1. **目标**——这一步做完系统多了什么能力
2. **范围**——做什么、明确不做什么
3. **前置条件**——依赖的步骤与外部条件
4. **实现方案**——按 agent / server / web / CI 分节，具体到文件、类型、函数、SQL、接口、组件
5. **接口与数据**——本步新增或变更的消息、REST、表
6. **验收标准**——可勾选的清单，含手工验证步骤
7. **风险与注意**
8. **产出物**——文件清单
9. **偏离记录**——实施时与设计方案不一致的地方（开工前为空）

---

## 7. 怎么用这些文档

每次开工一个步骤：把对应文档发给我，我按文档实现；做完对着"验收标准"逐条过；有偏离就写进第 9 节。步骤之间不跳——后面的文档默认前面的都已经落地。
