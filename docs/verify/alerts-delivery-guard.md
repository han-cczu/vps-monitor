## 已复现问题

`Deliver` 先查询整个到期待发列表，再分别读取渠道/事件并调用 HTTP。列表读取后，恢复告警会删除未发送行，停用渠道会更新 `enabled`，但旧候选仍会发送；完成时的 CAS 只能避免错误确认，不能撤销 HTTP 副作用。

确定性复现使用一个本地 `httptest` 接收器和两个按事件 ID 排序的候选。第一条 HTTP 请求的处理器同步完成第二条的恢复或渠道停用，然后返回；第二条此时已经在旧候选列表中。基线测试两个子例都失败：`sent 2 requests; stale candidate was sent after resolve/disable completed`，期望为 1 次。

## 修复与语义

- `ClaimAlertDelivery` 在事务首条条件 UPDATE 中检查行仍存在、原 `attempts` 未变、未发送、已到期、尚不足 3 次，以及渠道仍启用。领取时递增尝试次数并设置 30 秒租约；同事务读取最新渠道和事件，提交后返回。
- `DueAlertDeliveries` 只是候选快照。取消/停用若在领取事务前完成，旧候选无法领取，也不会发送。领取提交是本实现的发送尝试起点；随后发生的取消不能保证撤回已领取或在途请求。
- HTTP 在事务外执行，context 限制为 10 秒，短于租约。成功/失败完成时按领取后的 `attempts` 版本 CAS，不再递增尝试次数。旧尝试不能确认更新后的领取。
- 进程在领取后退出时，下一进程等待租约到期再重试；中断也消耗一次尝试，最多 3 次。正常失败仍从完成时刻起等待 30 秒。
- 一次性阈值提醒在创建时即有 `resolved_at`，仍应正常发送，不能用“事件已关闭”作为统一拒绝条件；状态类取消以 outbox 行删除为准。
- 外部发送与本地确认无法组成原子事务。若接收器已处理请求而进程在记录成功前退出，后续重试仍可能重复；本修复不声称外部消息恰好一次。
