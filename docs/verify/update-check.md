## 上线前补充回归

浏览器到面板的请求失败也纳入卡片展示状态：保留的版本标注为上次成功结果，隐藏旧的版本结论，直到后续请求成功才恢复。失败后的重试期间也不会提前恢复“已是最新”。`web/tests/update-check-card.test.mjs` 调用实际组件的点击处理和后续渲染，使用受控 API 与内存 hook 覆盖成功缓存 → 请求失败 → 重试中 → 恢复成功。补充修复后，前端 33 项测试、lint、生产构建及三个 Go 模块的全量测试和 vet 均通过；线上验证另记在本次部署记录中。

## 功能入口

| 入口 | 位置 | 说明 |
|---|---|---|
| 设置 → 站点 | 页面顶部 | 「版本与更新」卡片，下面是原有的站点设置表单 |
| 节点 | 表格上方 | 同一张卡片，下面仍是原有的「当前 Agent 发布版…」和「更新全部可更新节点」 |

卡片显示当前面板版本、面板携带的探针版本（`{VM_DATA_DIR}/agent/VERSION`）、更新源最新稳定版、检查时间、发布说明链接，以及面板与探针各自的结论。本次范围只有检查：面板升级仍走镜像部署，探针升级仍在节点页逐台或批量下发。

## 浏览器验收

环境：本机生产形态——`npm run build` 的产物拷进 `server/web/dist`（`go:embed`）后 `go build -ldflags "-X main.version=…" ./cmd/server`，监听 `127.0.0.1:9015`，数据目录里放一份 `agent/VERSION` 与假的探针产物文件（本地开发没有 `VM_AGENT_DIST`，同步会直接跳过）。用 headless Edge（`--headless=new` + CDP，Node 24 的 `WebSocket`）真实登录、真实鼠标点击、逐状态截图；桌面 1440×900，手机 390×844（`deviceScaleFactor=2`）。

用例覆盖六种结果，每次都用 `/api/health` 确认跑的是当次构建（避免浏览器在跟上一次的残留进程说话）：

| 用例 | 面板版本 | 更新源 | 携带的探针 | 卡片结论 |
|---|---|---|---|---|
| A | `v0.2.2` | `han-cczu/vps-monitor`（真实仓库，当前无 Release） | `v0.2.0` | 尚无稳定发布 |
| B | `v0.2.2` | `han-cczu/vps-monitor-missing`（不存在） | `v0.2.0` | 检查失败 |
| C | `v0.2.2` | `stretchr/testify`（最新稳定版 `v1.12.1`） | `v0.2.0` | 面板与探针都有更新 |
| D | `v1.12.1` | `stretchr/testify` | `v1.12.1` | 版本一致 |
| E | `v99.0.0` | `stretchr/testify` | `v99.0.0` | 当前版本更高 |
| F | `dev` | `stretchr/testify` | `v0.2.0-observe21` | 无法比较 |

六种状态在桌面两处入口和手机上都取到了同样的结论文本，没有出现「检查失败＝已是最新」：

- **待检查**：`最新稳定版 待检查`，无结论行，提示「点击检查更新，查询面板和探针的最新稳定版。」
- **尚无稳定发布**：`最新稳定版 尚未发布` +「更新源还没有稳定版本发布（草稿和预发布不计），暂时无法比较面板与探针版本。」
- **检查失败**：`最新稳定版 未获取到` +「更新仓库不存在或不是公开仓库，请核对更新源」，页脚改为「失败后 1 分钟可重试」。
- **有更新**：「面板有新版本 v1.12.1：先备份数据，再部署新版本。本功能只做检查，不自动安装或重启。」「更新源已有新探针 v1.12.1，面板携带的探针还是 v0.2.0：先部署携带新探针的面板安装包，再到节点页逐台或批量升级。」警示色，带「查看发布说明」。
- **版本一致**：「面板已是最新稳定版。」「面板携带的探针已是最新稳定版，可在节点页查看各节点版本后逐台或批量升级。」信息色。
- **当前版本更高**：「面板版本高于更新源的公开稳定版（v1.12.1），可能是尚未发布的构建。」
- **无法比较**：「面板版本 dev 无法与最新稳定版自动比较，请对照发布说明确认。」自定义后缀（`v0.2.0-observe21`）同样按无法比较处理，没有参与排序。

### 按钮与页面反馈

- 点击后按钮立即进入 loading：`disabled=true`，class 含 `MuiButton-loading` / `Mui-disabled`，按钮内可见 22×22 的 `MuiCircularProgress-root`，按钮自身仍是 82×36（不跳版）。`dist/update-check-accept/shots/D-loading-button.png` 是 3 倍放大的裁剪截图，能看见转圈。
- 冷缓存一次检查耗时 932ms（服务端日志 `dur_ms`），10 分钟内的第二次点击耗时 0ms，卡片补上「本次点击复用了缓存，没有重新查询更新源。」失败结果 1 分钟内重试同样命中缓存。
- 一次页面访问只发 `GET /api/updates`，每次点击只发一次 `POST /api/updates/check`；浏览器侧始终没有对 GitHub 的请求，也没有任何 `/agent/…` 下载。六次用例都没有 console 报错。
- 手机宽度下三个数据格改为纵向排列，告警文本自动折行，卡片不出现横向滚动；节点页原有的批量升级入口保持原样可见。

截图与驱动脚本在 `dist/update-check-accept/`（`dist/` 不进版本库）：`shots/` 下每个用例六张截图，另有 D 用例的 loading 按钮放大图和卡片文本 JSON；`cdp-drive.mjs` 是 CDP 驱动，`run.sh` 负责按用例重启面板并核对版本。

`internal/api/updates_test.go` 的端到端用例在带假 GitHub 的 HTTP 客户端上断言：未登录两个接口都 401；一次检查只发 2 个请求，且都指向 `https://api.github.com/repos/owner/repo/releases?…`、不带 Authorization；草稿、预发布、`sing-box-v…` 之类的标签被跳过；页 2 返回 503 时结果是失败而不是「最新版」；检查前后探针产物字节、`VERSION`、节点注册表和 `agent.*` 审计条目完全不变；响应里没有 queued/skipped/installed/downloaded 之类字段。`internal/updates` 另有用例覆盖：分页与缓存窗口、并发合并成一次上游请求、排队期间取消不改缓存、超时与 300 条扫描上限、失败保留上次成功版本、自定义/`dev` 版本不参与比较。

## 局限

- **验收是在本机做的**：没有推送、没有部署线上；公网面板仍是 `v0.2.2`，本次没有发布任何 Release，也没有真正升级过面板或探针。
- **「有更新」用的是第三方仓库**：项目仓库目前没有任何 Release，所以这一列用 `stretchr/testify`（最新稳定版 `v1.12.1`，27 条 Release，一页读完）当更新源，面板/探针版本用 `-ldflags` 注入的构建值代替。真实仓库第一次发 `vX.Y.Z` Release 之后，面板与探针共用同一个版本号序列，结论才具有实际意义。
- **国内机房到 `api.github.com` 的可达性没有验证**：本机可以直连，面板主机是否可达取决于机房出口；不通时卡片按「检查失败」显示，不误报最新。仓库里也没有代理/镜像更新源的实现，只有 `VM_UPDATE_REPOSITORY` 换仓库名这一条退路。
- **分页上限 300 条**：超过 3 页（每页 100 条）Release 的仓库会直接报「发布记录过多，无法确认最新版本，请到发布页核对」，这是有意的——宁可失败也不猜。
- 卡片只读更新源，不能强制绕过缓存；运维要在缓存窗口内重新查询只能在面板重启后（或等窗口过去）。这是为了守住 GitHub 未认证请求每 IP 每小时 60 次的限额。
